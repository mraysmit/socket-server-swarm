## 3. Decisions the user has made

Do not reopen these without asking.

1. Raft depends on no other plugin. It runs alone, with gossip, with kv, or with both.
2. Raft keeps its log, term and vote in its own files, on `raftlog`, never in kv.
3. The kv plugin does not change. On a Raft cluster it runs with `replication=off`.
4. A log entry is an instruction and its parameters, opaque to Raft. Applying it calls that instruction on the server.
5. Gossip never decides who votes and never carries Raft messages.
6. Raft messages go through the host's `KeepAliveClient`, with the server's ID as source, so the harness's network faults and call log apply.
7. `raft propose` is the only way to write. There is no shorthand such as `raft put`.
8. A direct `kv put` on a Raft member still succeeds, and changes that server alone. This is documented, not prevented.
9. Each phase ends with a demonstrable result and a passing suite, and the work stops for the user at the end of each.

## 4. How the plugin works (`plugins/raft-plugin/src/main/java/dev/mars/plugins/raft/`)

| Class | Job |
| --- | --- |
| `RaftNode` | The algorithm. Pure: takes an event and the time, returns ordered `Action`s. Pre-vote and check-quorum live here. |
| `RaftRunner` | One event loop per server: timers, a sender per peer, grouped syncs, proposals and reads waiting for answers. After every event it checks whether the node still leads, and answers what waits on it if not. |
| `RaftDisk`, `RaftLogDisk` | The disk contract, and its implementation on `raftlog`. The simulator's model disk passes the same contract tests. |
| `Applier` | Applies committed entries in order, through the server's own port. A success or an error caused by the command moves on. A missing plugin or no reply pauses and retries. It keeps a chained SHA-256 checkpoint over position, term, command and outcome. |
| `RaftPlugin` | The `raft` instruction: `bootstrap`, `propose`, `read`, `status`, `log`, and `vote` and `append` from peers. |
| `RaftConfig` | Settings from `raft-defaults.properties`, `-Draft.config`, and `server.<id>.` overrides. A misspelled setting is refused. |
| `RaftWire`, `TcpRaftTransport` | The JSON form of messages, and sending them. Optional fields (`round`, `preVote`) are sent only when set. |

Rules worth knowing before changing anything:

- **Durability.** The term and vote are saved before a vote is answered. Entries are synced before an `append` is confirmed, and before a leader counts itself. Syncs are grouped across waiting proposals, even past peers' messages, which a Phase 4 measurement showed matters: without it there was one sync per proposal.
- **Reads.** A leader answers a read only after it has committed an entry of its own term, and after a majority has answered since the read was asked. Only `read.operations` may run as a read, because a write run as a read would reach the leader alone.
- **Pre-vote.** A server that times out asks whether it would win the next term, without entering it, and nothing is saved anywhere. A server that has heard from a leader within `election.timeout.min.millis` refuses, and so does any leader. A refused reply carries the refuser's real term, which is followed; a granted one carries the term asked about, which is not.
- **Check-quorum.** A leader that has heard from no majority, itself included, for `election.timeout.max.millis` steps down. It keeps its term and its vote. Any reply counts, a refusal included.
- **What is not prevented or not built.**
  - A retried `propose` can apply twice.
  - There are no non-voting members and no authentication between peers.
  - The log is never compacted.
  - A server whose files are damaged cannot be restored. Clearing its directory is not safe: it would forget its vote and could vote twice in a term.

## 5. How the harness shows it (`socket-server-swarm`)

- `start <name> <n> raft` in the console, ticking Raft under Start a swarm on the page, or `"mode":"raft"` in `POST /api/swarms`, all start up to 9 servers as a cluster and bootstrap each one. `"without":"kv"` holds a plugin back, and `restart-with-all-plugins` gives it to one server.
- `RaftConfigFile` writes the harness's Raft settings: `data.dir` and `checkpoint.interval=8`. `KvConfigFile` turns kv replication off on Raft servers.
- `SwarmSnapshot` adds each server's `raft status`, and a `raftSummary` per Raft swarm. The summary gives the term and leader of the newest leader that can still commit, the stale leaders, the highest commit, and how many servers agree. A leader is stale when another leads in a newer term, or when a majority has moved past its term.
- `GET /api/servers/<id>/raft-log?from=&limit=` gives a page of a server's log. The harness asks it, so it does not show as a client's call.
- The page (`ui/swarm-observatory.html`) shows:
  - **Canvas:** a ring and the term on each leader, dashed amber for a stale leader, grey for what a frozen leader last said.
  - **Swarm line:** `raft: term · leader · commit · agree`.
  - **Details:** Raft facts and a voter table in the inspector, and a Raft log tab.
  - **Calls:** Votes and Appends filter chips. A line that carried a vote takes the vote's colour.
  - **Replay:** elections replay, and each change of leader is a tick on the timeline.
  - **Command tab:** a `raft` command reference, and a warning on a direct kv write to a Raft server.

## 8. The next task: Phase 7, changing the voters

The plan asks for this:
- Adding and removing one voter at a time, through the log.
- Add and Remove on a Raft swarm in the harness.
- A new server catches up before it gets a vote.
- A removed leader hands over cleanly.
- The simulator covers changes during partitions and crashes, including the known trap: a new leader must commit an entry of its own term before it starts a change.

The design proposed to the user, **not yet approved**:

1. **A change of voters is a log entry carrying the whole voter list with addresses.** A client cannot propose one, because every client command must name an instruction and this entry has none. Each server uses the newest voter list in its log, committed or not. Truncating the log back past one reverts to the one before, or to the bootstrap cluster.
2. **One change at a time.** A leader accepts a change only once it has committed an entry of its own term, and only while no other change is uncommitted.
3. **Adding a server.**
   - The harness starts the new server with a `join`, which gives it the cluster but no vote.
   - The leader replicates to it, and once it has caught up proposes the change that makes it a voter.
   - A server without a vote never stands.
4. **Removing a server.**
   - A removed follower stops standing, and pre-vote already keeps it from disturbing the others.
   - A leader that removes itself keeps leading until the change commits, without counting itself in majorities, then steps down.
5. **Order of work.**
   1. The simulator first: changes of voters during its schedules. Its election-safety and "durable on a majority" checks count against the voters in force.
   2. Two new broken variants: a change before committing in the leader's own term, and two changes at once.
   3. Then the node, the runner (its senders and addresses are fixed at start today), and the operations: `join`, `addVoter`, `removeVoter`.
   4. Then Add and Remove in the harness.
6. **What it unlocks.** A server whose files are damaged can be replaced at last: remove it, and add a fresh one.

Code that assumes fixed voters, found while starting:
- `RaftNode` keeps `voters` and `peers` as final lists.
- `RaftRunner` creates one sender per voter at start, from `cluster.voterIds()`.
- `TcpRaftTransport` builds its address map once.
- `RaftPlugin.bootstrap` refuses a server not among the voters.
- `RaftSimulator` uses a fixed `ids` list for every check.

No Phase 7 code has been written.

## 9. Open items, smaller than a phase

- **`raftlog` is used soundly, with two gaps.**
  - The plugin discards `raftlog`'s log output (it ships `slf4j-nop`), so a torn tail repaired at restart is never seen. Making that visible needs `raftlog` to report repairs through its API, which means a release of the user's library. That is the user's call.
  - `raftlog` also reads `verifyWrites`, `minFreeSpaceMb` and `maxPayloadSizeMb` from environment variables and a `raftlog.properties` file, so the plugin's behaviour can change from outside it. Any effect is loud (writes refused) or a slowdown, never lost data. Fixing the values in `RaftLogDisk.open` takes a few lines and a test, and is not done.
  - Syncing itself cannot be turned off: the builder refuses `false`.
- **The page has no automated tests** (section 7).
- **The vote-saving broken variant is rare with pre-vote on.** It is first caught at seed 56,238, against 2,753 with it off. The test with both on therefore searches 80,000 schedules, which adds about two minutes to the plugin's build.
- **The stale-leader window is now short.** With check-quorum, a cut-off leader is stale for at most a second. The harness test of the stale marking passed 10 of 10, but its window is narrow.
- **`FileRaftStorageLoggingTest` in `raftlog`** failed once in Phase 3, and is still unexplained.
- **The harness's snapshot endpoint takes about 51 ms on Linux** with gossip loaded, while the calls behind it take under 1 ms. Not looked into. An earlier claim that this was JDK `HttpServer`'s delayed ACK was wrong.
- **Leftover temporary folders:** `%TEMP%` holds 16 leftover `swarm-raft-*` entries, data folders and settings files, from harnesses that were force-stopped, which skips their cleanup. They are tiny. Deleting them in the shared temp folder was refused by the permission check, so they are left for the user.

## 10. Working agreements and gotchas

- **Test-first.** Red for the right reason, then green. A test that passes first time must be shown to fail by breaking the code it guards, then the code is restored. Phase 6 did this for each new rule.
- **Earlier tests stay unchanged** unless the change is announced and recorded in the plan. New constructors keep old call sites working: the 16-argument `RaftConfig`, the 5-argument `Timing` and the 4-argument `VoteRequest` all mean "pre-vote and check-quorum off".
- **Commits.** Do not commit unless asked. The user commits and pushes, often in the middle of a session, so check `git status` before saying anything is uncommitted.
- **Processes.** Never touch the user's processes. Stop only your own, identified by command line (`-Dexec.args=` and the plugin folders), and check none are left when finished.
- **Port 8088** is the harness the user looks at during a session. Leave a demo there only when asked to, and stop it when the user says to stop everything.
- **Power cuts.** Keep power cuts in proportion: never a headline risk. Partitions, crashes and restarts are what matter.
- **Line endings and shells.**
  - Python run in Git Bash on Windows writes CRLF, which the Linux container's `sh` rejects. Strip it with `sed -i 's/\r$//'` before mounting a script.
  - Bash heredocs with quotes in them can fail. Write the script to a file instead.
  - `surefire:test` does not recompile: use `mvn test` when checking that a broken change is caught.
- **Groovy quirks:**
  - Nested classes of classpath-source classes do not resolve from scripts, so `HistoryOp` is top level.
  - Inside a closure, `call(...)` means the closure's own `call`.
- **JSON** gives `BigInteger` for integers. Compare as `Number`.
- **Windows' loopback hid a 44 ms stall** in the host's keep-alive client: a request written in two pieces was held back by Nagle's algorithm and delayed ACK. It was fixed in Phase 4 with one write and `TCP_NODELAY`. Measure anything about time on Linux too.
