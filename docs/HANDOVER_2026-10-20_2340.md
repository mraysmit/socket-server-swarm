Decisions already made by the user, which should not be reopened without asking:

- No admin port. Config writes are HMAC-signed requests on the main port.
- The value is sent as a `valueText` string. A bad value is refused with INVALID_PARAMETERS.
- The secret comes from an owner-only file per key ID.
- The clock window is configurable. There is no separate writer switch. Overlay is per property.
- Reads are open. Config does not overshoot a ceiling (report, don't absorb).
- Limits are configuration and never hard-coded. Valid ranges are not "limits". Plugins validate themselves.
- A CLI is deferred.
- The host module owns the limits loader and a shared keep-alive client.

## 4. How Phase 2 works (kv plugin, `plugins/kv-plugin/src/main/java/dev/mars/plugins/kv/`)

- **Records.** Each is a `KvRecord` (key, JSON value, `Version(w,c,n)`, deleted flag). Order is by w, then c, then n. In Phases 1-2 `c` is always 0. `w` is strictly increasing per server and advanced past any received `w`. Newest write wins.
- **Deletions** are records that expire by their own timestamp against `namespace.kv.tombstone.retention.millis` (30 minutes). A server away longer than that can bring a deleted key back. This is documented behaviour.
- **Store.** `VersionedStore` has put, delete, get, apply (returns applied/ignored/rejected counts), a root hash (first 16 hex chars of SHA-256 over key/version/deleted in key order, excluding expired tombstones), `digestPage` and `range`.
- **Push.** `Replicator` pushes a local write to ALIVE peers on an executor. Failures are counted, not retried.
- **Anti-entropy.** `SyncRounds` runs `bootstrap()` at start (pull from one peer, then a second) and `round()` every `sync.round.millis`, choosing `sync.fanout` random alive peers. `Syncer` compares roots (`sync-root`). If they differ it exchanges paged digests (`sync-digest`, limited by `sync.max.bytes`, with a continuation key) and each side hands over what the other lacks (`apply`).
- **Swarm ID check.** Messages name the swarm, read from gossip `status`. A server in another swarm refuses them. A push goes without a swarm ID if gossip status cannot be read; a comparison always names it.
- **Peers.** `GossipPeers` calls gossip `members` (paged by `nextCursor`; the list includes the server itself, so it is filtered out) and keeps ALIVE ones.
- **Wire.** `TcpPeerLink` implements both `PeerLink` and `SyncLink` and opens a new connection per call. `KvWire` holds the JSON parsing and writing.
- **Config.** Bundled `kv-defaults.properties`, an optional file via `-Dkv.config`, `server.<serverId>.` overrides. Unknown or invalid keys are rejected and the key named. Settings: `replication`, `namespace.kv.max.key.length`, `max.value.bytes`, `max.records`, `tombstone.retention.millis`, `sync.round.millis`, `sync.fanout`, `sync.max.bytes`.
- **Operations** on the kv instruction: put, get, delete, list, apply, sync-root, sync-digest, status. `status` reports replication, pairs, deleted, counters, root and sync.

### Why `LoopbackGossip` is not a build dependency

kv has no gossip dependency in its pom. `LoopbackGossip` sends `"gossip"` text messages to the server's own port through the host's `TextMessageClient`. The `Gossip` interface is the seam; tests use stand-ins. The contract (instruction name, `members`, `nextCursor`, `assessment`, `status`) is implicit and only tests guard it. Replacing it with a direct in-process service is what `PLUGIN_SERVICES_DESIGN.md` describes.

## 5. How the harness uses it (`socket-server-swarm`)

- `SwarmMain`: `--kv-replicate` needs `--gossip` or `--gossip-fast`, otherwise it refuses with a message naming both.
- `KvConfigFile`: writes a config file and sets the JVM-wide `kv.config` property, created at the manager's first start.
- `SwarmManager`: constructor `(List<Path>, GossipSettings, boolean kvReplicate)`. It remembers servers that answered UNKNOWN_INSTRUCTION to the kv check (`knownWithoutKv`), so a plugin-free swarm is asked once per server.
- `SwarmSnapshot`: each server gets a `kv` entry (the plugin's `status` reply). Each swarm gets `kvSync` (replicating count, in-sync count, majority root; a tie goes to the smaller root so the page does not flicker).
- `ui/swarm-observatory.html`: a "kv: N of M in sync" line per swarm, kv facts in the inspector, "converged" and "suspect" events (a difference is reported only after two snapshots), a Try preset `kv status`, and the Command tab's command reference.
- Docs: `README.md`, `docs/user-guide.md`, `docs/swarm-tests.md` describe the above.

## 7. Working agreements and conventions

- **Strict TDD.** Red for the right reason, minimal green, refactor. Use a skeleton throwing `UnsupportedOperationException` to get a meaningful red. A test that passes first time is a guard and must be verified by breaking the code it guards (mutation), then reverting.
- Keep earlier tests passing unchanged unless the change is announced.
- **Do not commit unless asked.** The user commits themselves.
- Limits come from configuration, never code.
- Do not touch the user's own running processes. Kill only your own, identified by command line. Check that no swarm or Chrome test processes are left running when finished.
- Docs make no "new functionality" claims.
- Asserting on exception type alone is not enough: `NumberFormatException` is an `IllegalArgumentException`, so assert the message names the setting.

## 8. Known limits and Phase 3 scope

Known limits, all Phase 3:

- A write is pushed to every alive peer.
- Every push and comparison opens a new connection.
- The counter `c` is always 0.
- A replicated record over a limit is refused rather than absorbed (no soft ceiling).

Phase 3 as planned: forwarding with a fan-out limit, the shared keep-alive client moved into the host, the full clock counter, clock-skew refusal, the soft ceiling, and 100-server and partition tests. Ask the user for the go-ahead first.

## 9. Gotchas

- JSON decoding gives `BigInteger` for integers. Compare accordingly in tests (this caused several test bugs).
- Digest rows sent to `sync-digest` must be strictly key-ordered; the plugin refuses them otherwise.
- Gossip `members` includes the server itself and every assessment (ALIVE/SUSPECT/DEAD/LEFT/CANDIDATE).
- Windows: TIME_WAIT and keep-alive history shaped the connection handling. Opening a connection per call is part of why Phase 3 exists.
- Scripts in this environment: bash heredocs mangled escapes, so use files written with the Write tool. Files in the repo use CRLF line endings, so match them when doing exact-string edits.
- Port 8088 is the user's own harness UI. Run tests and browser checks on another port.
